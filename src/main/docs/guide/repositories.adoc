The three repository contracts expose the same operations and differ only in their return types. api:datarest.core.repositories.RestGenericRepository[] returns values directly and suits servlet or virtual-thread applications. api:datarest.core.repositories.ReactiveRestGenericRepository[] returns a Reactive Streams `Publisher` that emits at most one item, for use with any reactive library. api:datarest.core.repositories.ReactorRestGenericRepository[] returns a Project Reactor `Mono`.

The method names follow Micronaut Data's `CrudRepository`, so the programming model is familiar if you already use Micronaut Data. The difference is that there is no entity mapping: each call names the table, and the `type` argument decides how rows are deserialized.

Rows are serialized and deserialized with the application's JSON codec, so request bodies and result types can be any serializable class, including `Map<String, Object>` for partial updates.

Paging and sorting use Micronaut Data's `Pageable` and `Sort`, so the same objects can drive a Micronaut Data repository and a Micronaut Data REST repository. The `Sort` overload is shorthand for `findAll(table, Pageable.from(sort), type)`. Each gateway renders the sort in its own syntax, see <<ords>> and <<postgresql>>.

Listing operations return https://micronaut-projects.github.io/micronaut-data/latest/api/io/micronaut/data/model/Page.html[Micronaut Data `Page`] instances. The page returned for a `Pageable` keeps the request's sort, so `page.nextPageable()` can be passed straight back to `findAll`.

The `findById` and `update` operations return `null`, or complete empty, when no row matches, rather than failing.
